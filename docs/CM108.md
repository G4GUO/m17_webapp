# A CM108 fob as the interface

The Feather is the product interface to the analogue board. A CM108/CM119 sound
fob is the **bench** interface to it: about £5, plugged in, and the board can be
proven before a line of modem firmware has run on silicon.

Nothing about the modulation changes. `cm108.cpp` runs the same
`feather_tx_chain`/`feather_rx_chain` files the STM32F405 runs, vendored from
`m17_feather` under the same rule as `dsp/` and `feather_link.c`. What the fob
brings is real converters - 16-bit at 48 kHz, which is **better** than the
F405's 12-bit DAC and ADC - and a GPIO pin for PTT.

```
  TX   m17_mod_dibits() -> cm108_tx_dibits() -> TxChain -> 48 kHz -> fob playback
  RX   fob capture -> 48 kHz -> RxChain -> symbols -> m17_rx_symbols()
  PTT  hidraw vendor report, GPIO3 (LQFP pin 13), padded around the audio
```

## Wiring

| fob | analogue board |
| --- | --- |
| headphone out (playback) | modulator input - through a level control, set for the board's rated deviation |
| mic in (capture) | discriminator output - **turn the +20 dB mic boost off**, and disable the internal mic-to-output mixer or the receiver hears its own transmitter |
| GPIO3 + a small NPN/opto | PTT (most radios and boards want a pull to ground) |
| GND | GND |

The pins are 3.3 V CMOS with a few milliamps of drive: they key a transistor, not
a radio. On most £4 fobs GPIO3 is already wired to the LED, so the trace has to
be cut.

## PTT

The codec exposes its GPIO through a second USB interface - HID - which `usbhid`
already binds, so there is no driver, just `/dev/hidrawN`. The report is five
bytes:

```
  io[0] = 0
  io[1] = 0
  io[2] = data    bit(n-1) = level of GPIO n
  io[3] = mask    bit(n-1) = 1 means GPIO n is an output
  io[4] = 0
```

Four bytes returns `EPIPE`; five is what the chip wants. GPIO3 is `0x04` in both
bytes. The mask bit stays set on unkey so the pin stays an output, just low.

Reading it needs permission:

```
  # /etc/udev/rules.d/99-cm108.rules
  KERNEL=="hidraw*", ATTRS{idVendor}=="0d8c", MODE="0660", GROUP="audio"
```

`cm108_hid.cpp` looks the node up by vendor id (`0d8c` C-Media, `0c76` SSS
clones, `1209` the AIOC, which emulates a CM108 on an STM32) or takes
`CM108_HID=/dev/hidrawN`.

## Keying, which is the whole difficulty

On the Feather, PTT and dibits travel down one endpoint and the board refuses to
key without both, so the two cannot drift apart. On a fob they are a HID report
and an isochronous stream with **no ordering relationship at all**. The only
thing that makes it work is doing it in this order, which `cm108_key()` does:

1. 10 ms of silence into the playback stream, so the stream is already running
   when the radio keys;
2. the PTT edge;
3. another 30 ms of silence - on the air, which is time the far end spends
   settling before the preamble arrives;
4. symbols;
5. on unkey: the modulator's 31-symbol filter tail, a further 40 ms of silence,
   then the PTT edge down.

Both halves are adjustable: `CM108_PREKEY_MS` (default 40, including the 10 ms
buffered first) and `CM108_TAIL_MS` (default 40). Cut them down once the board's
key-up delay is known; a slow radio needs them longer.

## Rate

48000 exactly, on `hw:` and never `plughw:`/`default` - a plug resampler puts a
fraction of a percent of rate error into every burst, which is a message that
decodes at 97% of its frames. The open fails rather than resampling.

`CM108_PCM` selects the playback device (default `hw:1,0`, so check `aplay -l`);
`CM108_PCM_IN` overrides capture for the split cases (`snd-aloop`, or a separate
ADC). `CM108_GPIO` selects a different pin.

## Running it

Same as `-r feather-loop`: a `config.txt` with `rf`, `tf`, `sa`, `mode radio`
(not `mode gate`) and no `conn` line, then

```
  m17web -r cm108 -w 8111 -www /path/to/m17gismo/www
  python3 tools/wstest.py --port 8111 --steps 3 --cmd "sms hello from the fob" --duration 6
```

The status line in the log and the UI reports the device, symbol and dibit
counts, and the ALSA underrun/overrun counters - a rising underrun count while
transmitting means the host cannot feed the stream and the padding is too short
for this machine.

## What is tested, and what is not

`make cm108test` (19 checks, no sound card, no fob) drives the back end against a
fake PCM whose playback ring is its capture ring, and a fake hidraw node:

- a failed open leaves the back end closed and says why;
- keying writes exactly one GPIO3 report, with at least 10 ms of *silence*
  already in the stream when the PTT edge goes;
- 192 dibits produce exactly 1920 frames;
- the baseband is the real thing: peak 1.378, largest sample step 0.431;
- the same stream read back through the receive chain gives 147/147 hard
  decisions correct at lag 0;
- unkey drains the filter tail (2551 frames) and only then drops PTT.

**Not tested here:** the fob's converters, its analogue front end, the hidraw
path on a real device, and ALSA itself. First session with hardware: `arecord`
and `aplay` at 48 kHz to prove the device, then `CM108_PCM=hw:N,0`, then a
message, then check the PTT edge on a scope against the first sample.

## Feather or fob

| | CM108 fob | Feather |
| --- | --- | --- |
| cost | ~£5 | PCBA |
| converters | 16-bit, 48 kHz | 12-bit, 48 kHz |
| PTT | separate HID report, jitter, needs padding | same endpoint as the data, board-enforced |
| COS | none (GPIO3 is an output) | no PTT input either, by design |
| DSP | host | board |
| interfaces | standard USB audio - any program can use it | ours alone |
| use for | proving the analogue board now, and as a sound-card radio | the product |

`radio_keyed()` returns false for this back end, for the same reason it does for
the Feather: GPIO3 is an output, there is no PTT input to read, and falling
through to the software flag makes the hardware PTT monitor key the transmitter
in a loop.
